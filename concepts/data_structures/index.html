    Data Models & Storage Architecture¶

    Efficiently processing serial block-face datasets requires scalable storage models that bridge file-based microscope outputs with high-speed relational queries and tiled volumetric formats.

    Filesystem Layout¶

    A standard em_inspection project links an Acquisition Directory (read-only raw data from the microscope) to a Processing Directory (scratch and working directory for offsets, meshes, and stitched outputs).

    <sbem_root_dir>/ (Acquisition Directory)
├── sections/
│   ├── s00000_g0000/
│   │   ├── tile_id_map.json       # 2D grid matrix mapping coordinates to tile IDs
│   │   ├── 000.tif                # Individual raw 16-bit or 8-bit tile images
│   │   ├── 001.tif
│   │   └── ...
│   ├── s00001_g0000/
│   └── ...
├── metadata/
│   └── acquisition_params.yaml    # Pixel size, beam energy, dwell time
└── missing_sections.yaml          # Generated by Stage 1 validation

<proc_dir>/ (Processing Directory)
├── coarse_offsets.db              # DuckDB database containing all translational shifts
├── grid_0_gs/
│   ├── s00000_g0000/
│   │   ├── cx_cy.json             # 4D coarse offset matrix for this section
│   │   ├── coarse_mesh.npz        # Relaxed spring mesh coordinates
│   │   ├── margin_masks.npz       # Zero-weight boundary mask
│   │   ├── fine_flows.npz         # Dense patch optical flow fields
│   │   ├── fine_mesh.npz          # Final regularized elastic mesh
│   │   ├── s00000_g0000.zarr      # Stitched and warped section image
│   │   └── thumb_s00000_g0000.tif # Downscaled overview thumbnail
│   └── ...
└── tile_stitching_config.yaml     # Active configuration snapshot

    The DuckDB Coarse Offsets Registry¶

    Rather than parsing tens of thousands of individual JSON or text files across network-attached storage (NAS), em_inspection consolidates all tile translational shift vectors into an embedded DuckDB database.

    Relational Schema¶

    CREATE TABLE coarse_offsets (
    tile_id         VARCHAR,      -- Identifier for the primary reference tile (e.g. '362')
    section_number  INTEGER,      -- Physical section cutting index Z (e.g. 13212)
    h_dx            REAL,         -- Horizontal overlap X displacement (pixels)
    h_dy            REAL,         -- Horizontal overlap Y displacement (pixels)
    v_dx            REAL,         -- Vertical overlap X displacement (pixels)
    v_dy            REAL          -- Vertical overlap Y displacement (pixels)
);

CREATE INDEX idx_offsets_tile ON coarse_offsets (tile_id);

    High-Performance Querying & Outlier Analytics¶

    Because DuckDB is a columnar engine, querying a full \(Z\)-trace of 25,000 sections for a specific tile overlap executes in under \(10\text{ ms}\):

    # Extract the full drift curve for tile 362 across all sections
query = """
    SELECT section_number, h_dx, h_dy, v_dx, v_dy 
    FROM coarse_offsets 
    WHERE tile_id = ? 
    ORDER BY section_number ASC
"""
df = con.execute(query, [str(tile_id)]).df()

    Atomic Scratch Compilation Pattern¶

    Large SBEM datasets frequently reside on networked storage mounts (SMB/NFS) where SQLite or DuckDB concurrent writes can suffer lock contention or volume latency.

    em_inspection implements an atomic build pattern: 1. When computing coarse offsets or updating curated vectors in batch, the database is compiled in local high-speed temporary storage (/tmp/..._duckdb_build/). 2. After indexing and schema validation complete, the file is atomically transferred to the network processing directory via shutil.move().

    Section-Level Export: 4D Coarse Offset Matrix (cx_cy.json)¶

    To interface seamlessly with SOFIMA and distributed cluster execution workers, each section's verified offsets can be exported into an individual cx_cy.json file.

    The coordinate structure is stored as a 4-dimensional matrix of shape:

    \[\text{Shape} = (2,\, 2,\, Y,\, X)\]

    Where: - Axis 0 (\(2\)): Overlap direction (\(0 = \text{Horizontal Overlap } H\), \(1 = \text{Vertical Overlap } V\)) - Axis 1 (\(2\)): Shift vector component (\(0 = \Delta x\), \(1 = \Delta y\)) - Axis 2 (\(Y\)): Grid row index - Axis 3 (\(X\)): Grid column index

    {
  "section_id": "s00414_g0000",
  "grid_shape": [20, 15],
  "offsets_4d": [
    [
      [[0.0, -145.2, ...], [0.0, -144.8, ...]],
      [[0.0, -21.4, ...],  [0.0, -20.9, ...]]
    ],
    [
      [[395.1, 396.0, ...], [394.8, 395.2, ...]],
      [[-175.3, -174.9, ...], [-176.1, -175.5, ...]]
    ]
  ]
}

    Configuration Models (pydantic)¶

    All pipeline configurations are strictly validated at runtime using Pydantic models:

    • ExpConfig: Defines paths, physical resolution (\(nm/\text{pixel}\), slice thickness in \(nm\)), section ranges, and grid geometry.
    • RegistrationConfig: Controls cross-correlation filter sizes, CLAHE clip limits, and block-matching patch dimensions.
    • MeshIntegrationConfig: Controls numerical relaxation parameters for the SOFIMA spring-mass system (\(\Delta t\), damping coefficient \(\gamma\), spring constant \(k\)).
    • WarpConfigStitching: Governs interpolation margins, CLAHE settings, and worker concurrency.
